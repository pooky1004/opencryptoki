# Token NCMP — 세션 상태 관리 및 저장 항목 (동작 모델)

- **작성일**: 2026-09-02
- **대상 독자**: FX3 펌웨어/엔진 설계자, `ncmpd`·STDLL 개발자
- **관련 문서**: [`architecture.md`](architecture.md) · [`SUMMARY.md`](SUMMARY.md) ·
  [`stdll-call-flow.md`](stdll-call-flow.md)

> 이 문서는 **NCMP 토큰(FX3 디바이스/엔진) 자체**가 어떻게 동작하고 무엇을
> 관리해야 하는지를 규정한다. 특히 **여러 애플리케이션의 여러 스레드가 동일
> 토큰에 동시에 접근**하고, 토큰이 **세션별 연산 중간 상태를 유지**했다가 다음
> 명령이 오면 이전 상태를 로드해 이어서 처리하는 모델을 기준으로,
> **비휘발성(NVM) / 휘발성(RAM)** 저장 항목을 구분해 설명한다.

---

## 1. 목적과 범위

NCMP 토큰은 다음을 만족해야 한다.

1. **동시 접근**: 다수 프로세스(애플리케이션) × 다수 스레드가 같은 물리 토큰을
   동시에 사용한다. 호스트 측 `ncmpd`가 이들을 단일 USB 링크로 다중화하지만,
   토큰 내부에서도 **명령들이 인터리빙(interleaving)** 되어 도착한다.
2. **세션별 상태 유지**: 하나의 연산(예: 멀티파트 해시, AES-GCM, 스트리밍 서명)은
   `Init → Update* → Final`처럼 **여러 명령에 걸쳐** 진행된다. 토큰은 각 세션이
   "어디까지 무엇을 하고 있었는지"를 **중간 상태(context)** 로 보관한다.
3. **상태 로드-처리-저장 사이클**: 특정 세션의 다음 명령이 도착하면 엔진은 그
   세션의 이전 컨텍스트를 **load** 하여 이어서 처리하고, 처리 후 갱신된 상태를 다시
   **save** 한다. 명령과 명령 사이에는 다른 세션이 엔진을 점유할 수 있다.

이 문서는 그 동작을 실현하기 위해 토큰이 관리해야 하는 모든 상태를, **전원이
꺼져도 유지되어야 하는 것(NVM)** 과 **세션·부팅 수명 동안만 유지되는 것(RAM)** 으로
나누어 정의한다.

## 2. 동작 모델

### 2.1 다중 접근 구조

```
App A ─ thread ┐                             ┌ 세션 컨텍스트 슬롯 (RAM)
App A ─ thread ┤                             │  sess#1 ▸ [engine state]
App B ─ thread ┼─▶ ncmpd (호스트 다중화) ─USB─▶ MCU ─┼  sess#2 ▸ [engine state]
App B ─ thread ┤   (SHM 큐 + comm_thread)     │  sess#3 ▸ [engine state]
App C ─ thread ┘                             └  ...
                                             암호 엔진 + 4× SRAM 컨테이너 + NVM
```

- **호스트(ncmpd)**: 여러 프로세스/스레드의 요청을 슬롯별 MPSC 큐에 모아 순서대로
  USB로 전송한다. 각 프레임은 `session_id` / `sequence_id` / `command_id`를
  가진다(→ [`architecture.md`](architecture.md), `ncmp_wire.h`).
- **토큰(MCU/엔진)**: 최대 4개의 SRAM 컨테이너로 들어온 명령을 라운드로빈으로
  실행한다. 명령마다 헤더의 `session_id`로 **어느 세션의 작업인지**를 식별한다.
- **핵심**: 토큰은 명령을 **무상태(stateless) 단발**로 처리하지 않는다. 세션마다
  진행 중인 연산의 **엔진 상태**를 보관하고, 같은 `session_id`의 후속 명령에서 그
  상태를 이어받는다.

### 2.2 세션 기반 상태 유지

PKCS#11 연산은 대부분 **상태 기계**다.

```
C_DigestInit(sess)      →  MLDSA/SHA 컨텍스트 생성, mech·초기 상태 저장
C_DigestUpdate(sess, d) →  이전 누적 상태 load → d 흡수 → 갱신 상태 save
C_DigestUpdate(sess, d) →  (다른 세션 명령이 사이에 끼어들 수 있음)
C_DigestFinal(sess)     →  최종 상태 load → 출력 생성 → 컨텍스트 해제
```

토큰은 각 활성 세션에 대해 **"현재 진행 중인 연산 종류 + 그 연산의 중간 상태"** 를
보관해야 한다. 이 중간 상태가 이 문서에서 말하는 **세션별 연산 컨텍스트**이며,
동시 접근 환경에서 세션 간에 **격리(isolation)** 되어야 한다.

### 2.3 명령 처리 흐름 (load → process → save)

```
1. 수신     : 프레임 파싱 (session_id, sequence_id, command_id, params)
2. 인증검사 : 해당 연산이 요구하는 로그인/권한 상태 확인
3. 컨텍스트 : session_id로 세션 컨텍스트 조회
              - 진행 중 연산이 있으면 엔진 상태 load
              - Init 명령이면 새 컨텍스트 할당
4. 실행     : 암호 엔진 수행 (필요 시 NVM의 키/속성 참조)
5. 상태저장 : 갱신된 엔진 상태를 세션 컨텍스트에 save
              - Final/오류/세션종료면 컨텍스트 해제 + 민감정보 소거
6. 응답     : ack(CKR_*) + 출력 파라미터를 프레임으로 반환 (sequence_id 매칭)
```

이 사이클에서 **무엇을 어디에 저장하느냐**가 이 문서의 핵심이다.

## 3. 저장 위치 판단 원칙

| 기준 | 비휘발성(NVM) | 휘발성(RAM) |
|------|---------------|-------------|
| 전원 차단 후에도 유지되어야 하는가 | 예 | 아니오 |
| 토큰의 "영속 자산"인가 (키·PIN·정체성) | 예 | 아니오 |
| 세션/연결/부팅 수명에만 의미가 있는가 | 아니오 | 예 |
| 재생성 가능한가(다음 연결에서 다시 만들면 되는가) | 아니오 | 예 |
| 잦은 갱신으로 쓰기 내구성(wear)이 문제되는가 | 회피 대상 | 자유 |

> **원칙 1**: 세션 컨텍스트(연산 중간 상태)는 **휘발성**이다. 세션은 연결
> 수명(프로세스/토큰 리셋)에 종속되며, 끊기면 진행 중 연산은 폐기된다(PKCS#11
> 의미론과 일치).
> **원칙 2**: 키·PIN·정체성 등 **영속 자산**은 **비휘발성**이다.
> **원칙 3**: 민감한 휘발성 데이터(세션 키, 컨텍스트 내 평문/중간 다이제스트)는
> 해제 시 **즉시 0으로 소거(zeroize)** 한다.

## 4. 비휘발성(NVM) 저장 항목

전원이 꺼져도 유지되어야 하는 토큰의 영속 상태.

| # | 항목 | 개요 | 갱신 빈도 |
|---|------|------|-----------|
| N1 | 토큰 정체성 | label·serial·manufacturer·model·HW/FW 버전 | 매우 낮음 |
| N2 | 토큰 플래그/상태 | 초기화 여부, PIN 초기화 여부, 잠금 상태 | 낮음 |
| N3 | SO PIN | 보안담당자 PIN 검증자(해시/솔트) + 재시도/잠금 | 낮음 |
| N4 | User PIN | 사용자 PIN 검증자(해시/솔트) + 재시도/잠금 | 낮음 |
| N5 | 토큰 객체(영속 키) | CKA_TOKEN=TRUE 키·데이터 객체와 전 속성 | 중간 |
| N6 | 객체 핸들/인덱스 | 객체 ID ↔ 저장 위치 매핑, 슬롯 할당표 | 중간 |
| N7 | 마스터키/랩핑키 | 객체 암호화용 키 계층(KEK) | 매우 낮음 |
| N8 | 단조 카운터/감사 | 객체 ID 시퀀스, 부팅/셀프테스트 카운터, 감사로그 | 다양 |

### N1. 토큰 정체성 (label / serial / manufacturer / model / 버전)
- **내용**: `CK_TOKEN_INFO`의 고정 필드. `NCMP_CMD_VD_TOKEN_INFO`로 호스트가
  부팅 시 스캔해 SHM에 캐시한다(→ [`architecture.md`], `NCMP_TokenIdentity`).
- **왜 NVM**: 물리 토큰의 신원. 호스트의 **슬롯↔토큰 바인딩(label/serial 매칭)** 의
  근거이므로 재부팅 후에도 동일해야 한다.
- **주의**: serial은 공장에서 부여되며 불변. label은 `C_InitToken`으로 변경
  가능하므로 초기화 시 갱신된다.
- **`C_InitToken` 절차(set→read-back→validate→persist)**: STDLL은 (1) SO PIN·label을
  토큰에 설정(`INIT_TOKEN`)하고, (2) `VD_TOKEN_INFO`로 label을 **다시 읽어와 정밀
  검증**한 뒤, (3) 검증된 정체성을 `nv_token_data`에 캐시하고 `save_token_data()`로
  영속화한다. 사용한 **임시 SO PIN·label 버퍼는 즉시 zeroize**한다(아래 보안 원칙).

### N2. 토큰 플래그 / 초기화 상태
- **내용**: `CKF_TOKEN_INITIALIZED`, `CKF_USER_PIN_INITIALIZED`,
  `CKF_SO_PIN_LOCKED`/`USER_PIN_LOCKED`, `CKF_LOGIN_REQUIRED`,
  `CKF_USER_PIN_COUNT_LOW`/`FINAL_TRY`/`LOCKED` 등.
- **왜 NVM**: PIN 상태·잠금은 전원 차단으로 **초기화되면 안 된다**(재부팅으로
  잠금을 우회하는 공격 방지). `C_GetTokenInfo`가 이 플래그를 보고한다.

### N3 / N4. SO PIN / User PIN (검증자 + 재시도 카운터)
- **내용**: PIN 원문이 아니라 **검증자**(솔트 + 반복 해시/HMAC 또는 PBKDF 결과),
  재시도 남은 횟수, 잠금 여부. 초기 PIN 초기화·`C_SetPIN`/`C_InitPIN`로 갱신.
- **왜 NVM**: 인증은 전원 사이클과 무관하게 강제되어야 한다. **재시도 카운터도
  NVM** 이어야 리셋으로 무제한 시도를 막을 수 있다(카운터는 시도 **직전** 감소,
  성공 시 복구하는 순서로 기록).
- **보안**: 원문 PIN은 절대 NVM/로그에 남기지 않는다. 비교는 상수시간으로.
- **호스트 매핑**: `NCMP_CMD_LOGIN/INIT_PIN/SET_PIN/INIT_TOKEN`(→
  [`SUMMARY.md`] 2.4). mock은 평문 비교이나 실제 토큰은 검증자 방식이어야 한다.
- **secure-key 토큰**: `token_specific.secure_key_token = TRUE`. 즉 **모든 PIN·키
  비밀은 물리 토큰이 소유**하고, STDLL은 프록시로서 임시로 보유한 비밀 버퍼(예:
  `C_InitToken`의 SO PIN·label)를 사용 직후 **영구 소거(zeroize)** 한다.
- **로그인 플래그**: `LOGIN` 요청은 SO/User 역할 외에 부가 플래그를 함께 싣는다 —
  **protected-auth**(PIN을 토큰 패드에서 입력, 와이어 PIN 비움)와
  **context-specific**(`CKU_CONTEXT_SPECIFIC`: 로그인 상태를 바꾸지 않고 현재
  사용자의 PIN을 재검증; 미로그인 시 `CKR_USER_NOT_LOGGED_IN`).

### N5. 토큰 객체 (영속 키 · 데이터 객체)
- **내용**: `CKA_TOKEN=TRUE`인 모든 객체와 **전 속성**:
  - **키 재료**: 우리 mechanism 기준 — AES 키(`CKA_VALUE`), generic secret,
    **ML-KEM/ML-DSA 키페어**(공개/개인 블롭 = `CKA_VALUE`, `CKA_SEED`,
    파라미터셋 `CKA_PARAMETER_SET`).
  - **속성**: `CKA_CLASS`, `CKA_KEY_TYPE`, `CKA_ID`, `CKA_LABEL`,
    `CKA_PRIVATE`, `CKA_SENSITIVE`, `CKA_EXTRACTABLE`, `CKA_TOKEN`,
    `CKA_ENCRYPT/DECRYPT/SIGN/VERIFY/DERIVE/ENCAPSULATE/DECAPSULATE`,
    `CKA_VALUE_LEN` 등 사용 정책 비트.
- **왜 NVM**: 토큰 객체의 정의(PKCS#11)는 "세션·연결과 무관하게 토큰에 영속".
- **보안**: 개인/비밀 키 재료는 **N7의 마스터키로 암호화**해 저장(at-rest 암호화),
  `CKA_SENSITIVE=TRUE`/`CKA_EXTRACTABLE=FALSE`면 평문 반출 금지.
- **구분**: `CKA_TOKEN=FALSE`(세션 객체)는 NVM이 아니라 **휘발성**(→ V4).

### N6. 객체 핸들 / 인덱스 / 슬롯 할당표
- **내용**: 객체 식별자 ↔ NVM 저장 위치(오프셋/블록) 매핑, 사용/여유 슬롯 비트맵,
  객체별 메타(생성시각, 소유 등).
- **왜 NVM**: 영속 객체를 재부팅 후에도 찾아 로드하려면 인덱스가 유지돼야 한다.
- **주의**: PKCS#11 **객체 핸들(`CK_OBJECT_HANDLE`)** 자체는 애플리케이션
  세션 스코프의 휘발성 번호다(→ V4). 여기서의 "핸들/인덱스"는 **토큰 내부의
  영속 객체 ID↔저장위치** 매핑을 뜻한다. 둘을 혼동하지 말 것.

### N7. 마스터키 / 랩핑키 (KEK 계층)
- **내용**: 토큰 객체의 개인/비밀 키 재료를 암호화하는 최상위 키(들).
- **왜 NVM**: 없으면 저장된 키를 복호할 수 없다. 가능하면 **PUF/보안요소/전용
  키스토어**에 봉인하고, PIN에서 유도한 키로 한 번 더 래핑(사용자 데이터 보호).
- **보안**: 마스터키는 절대 평문 반출 금지. 교체(rotation) 시 전체 객체 재암호화
  절차 필요.

### N8. 단조 카운터 / 감사 로그
- **내용**: 객체 ID 시퀀스(재사용 금지), 부팅 카운터, 셀프테스트 결과/시각,
  실패 이벤트 감사 로그(선택).
- **왜 NVM**: 롤백/재사용 공격 탐지·감사 추적. 단조성이 핵심이라 전원과 무관해야
  한다.

## 5. 휘발성(RAM) 저장 항목

전원 차단·토큰 리셋으로 사라져도 되는(사라져야 하는) 런타임 상태. **세션별 연산
중간 상태(V3)** 가 이 문서의 핵심이다.

| # | 항목 | 개요 | 수명 |
|---|------|------|------|
| V1 | 세션 테이블 | 활성 세션 목록과 메타(session_id, 소유, 상태, R/W) | 세션 |
| V2 | 인증/로그인 상태 | 현재 로그인 사용자 유형, 인증된 세션 집합 | 로그인 |
| V3 | **세션별 연산 컨텍스트** | 진행 중 연산의 엔진 중간 상태(핵심) | 연산 |
| V4 | 세션 객체 | `CKA_TOKEN=FALSE` 객체와 세션 스코프 핸들 맵 | 세션 |
| V5 | 엔진 작업 버퍼 | 복호 평문, DMA/컨테이너 버퍼, 임시 스크래치 | 명령 |
| V6 | RNG 상태 | DRBG 내부 상태(시드/카운터) | 부팅 |
| V7 | 전송/스케줄 상태 | 컨테이너 점유, in-flight, sequence 추적 | 명령 |
| V8 | 복호된 마스터키 캐시 | at-rest 키의 런타임 사본 | 부팅/로그인 |

### V1. 세션 테이블
- **내용**: `session_id → { 소유 애플리케이션/연결, 상태(R/O·R/W), 로그인 관점,
  진행 중 연산 참조(V3), 생성시각 }`. 상한: 슬롯당 8, 전체 32
  (→ `ncmp_limits.h`).
- **왜 휘발성**: 세션은 연결 수명에 종속. 연결이 끊기거나 토큰이 리셋되면 모든
  세션은 사라진다(PKCS#11: `C_CloseSession`/`C_CloseAllSessions`).
- **동시성**: 여러 스레드가 **서로 다른 세션**으로 동시에 진입하므로 세션 테이블
  접근은 락/원자연산으로 보호. 세션 간 컨텍스트는 절대 공유되지 않는다.

### V2. 인증 / 로그인 상태
- **내용**: 현재 로그인 사용자 유형(SO/User/미로그인)과 **로그인이 적용되는
  범위**. PKCS#11에서 로그인 상태는 **애플리케이션(=연결)의 모든 세션에 공유**된다.
- **왜 휘발성**: 로그인은 세션/연결 수명 동안만 유효. 토큰 리셋 시 로그아웃 상태로
  복귀해야 한다. 단, **PIN 검증자·재시도 카운터(N3/N4)** 는 NVM.
- **주의**: 다중 애플리케이션이 동시에 접근하므로, "누가 로그인했는가"는
  **연결(애플리케이션) 단위**로 구분해 관리해야 한다(한 앱의 로그아웃이 다른 앱의
  세션에 영향 주지 않도록).
- **context-specific 재인증**: `CKU_CONTEXT_SPECIFIC` 로그인은 로그인 상태를
  바꾸지 않고 **현재 사용자의 PIN을 즉석 재검증**하는 흐름(예:
  `CKA_ALWAYS_AUTHENTICATE` 키 사용 직전)이다. 성공해도 V2 상태는 그대로다.

### V3. 세션별 연산 컨텍스트 ★ (진행 중 연산의 중간 상태)
"세션 별로 무엇을 하고 있었는지"를 담는 핵심 항목. 각 활성 세션은 **최대 몇 개의
동시 연산 컨텍스트**(예: 서명 1 + 암호화 1 + 다이제스트 1)를 가질 수 있다.

공통 필드:
- `session_id`, 연산 종류(digest/encrypt/decrypt/sign/verify/derive), mechanism,
  연관 키 참조(핸들), 진행 단계(Init/Update/Final), 누적 입력 길이.

mechanism별 유지 상태(우리 토큰의 지원 집합 기준) — **6절 상세** 참조:
- **AES-GCM**: 키/IV, GHASH 누적자, 블록 카운터(J0), 처리한 AAD·평문 길이, 태그
  진행 상태.
- **AES-CTR**: 키, 현재 카운터 블록, 스트림 오프셋(부분 블록 잔여).
- **SHA-256/512, SHA3-***: 해시 내부 상태(체인 변수), 부분 블록 버퍼, 총 길이.
- **SHAKE(XOF)**: 흡수/스퀴즈 상태, 이미 출력한 바이트 수(요청 길이만큼 이어서).
- **ML-DSA(hash-then-sign 스트리밍)**: 프리해시 컨텍스트, 도메인/컨텍스트 문자열,
  hedge/deterministic 모드, 키 참조.
- **ML-KEM**: 대부분 단발(encaps/decaps)이라 컨텍스트 유지 최소. 필요 시 입력
  누적만.

- **왜 휘발성**: 진행 중 연산은 **연결이 끊기면 폐기**되는 것이 PKCS#11 의미론.
  또한 중간 다이제스트·평문·키스트림은 **민감정보**라 오래 남기면 안 된다.
- **격리**: 컨텍스트는 반드시 `session_id`로 격리. 인터리빙된 다른 세션의 명령이
  절대 이 상태를 건드리면 안 된다.
- **소거**: Final/오류/세션종료 시 즉시 zeroize 후 반환.

### V4. 세션 객체 (`CKA_TOKEN=FALSE`) 및 세션 스코프 핸들 맵
- **내용**: 세션 수명 객체(예: 방금 파생된 공유비밀 키, 임시 AES 키)와
  **애플리케이션에 노출되는 `CK_OBJECT_HANDLE` ↔ 실제 객체** 매핑.
- **왜 휘발성**: 세션 객체는 세션 종료 시 사라진다. 핸들 번호는 연결 스코프의
  일시적 식별자다(재부팅/재연결 시 동일 보장 없음).
- **연계**: ML-KEM encaps/decaps가 만드는 **공유비밀 키 객체**는 템플릿의
  `CKA_TOKEN`에 따라 세션 객체(V4) 또는 토큰 객체(N5)가 된다.

### V5. 엔진 작업 버퍼 (복호 평문 · DMA · 스크래치)
- **내용**: 명령 처리 중의 입출력 버퍼, SRAM 컨테이너, 복호된 평문, 임시 키 확장.
- **왜 휘발성**: 명령 단위 임시 데이터. **복호 평문·키 재료는 사용 후 즉시 소거.**

### V6. RNG / DRBG 상태
- **내용**: DRBG 내부 상태(엔트로피 시드, 카운터, reseed 카운터).
- **왜 휘발성**: 부팅 시 하드웨어 엔트로피로 시드. 상태를 NVM에 남기면 예측/재사용
  위험. RNG(`NCMP_CMD_RNG`)와 키 생성이 이 엔진을 사용.

### V7. 전송 / 스케줄 상태
- **내용**: 4개 SRAM 컨테이너 점유 현황, in-flight 명령 수, 라운드로빈 커서,
  `sequence_id` 매칭 테이블.
- **왜 휘발성**: 순수 런타임 흐름 제어. 호스트 측 통계
  (`in_flight_cnt`/`stats_*`)와 대응(→ [`architecture.md`]).

### V8. 복호된 마스터키 / 키 캐시
- **내용**: N7 마스터키를 부팅(또는 로그인) 시 복호해 RAM에 둔 런타임 사본,
  자주 쓰는 키의 복호 캐시.
- **왜 휘발성**: 평문 키는 절대 NVM에 상주하면 안 된다. 유휴 시/리셋 시 소거.

## 6. 세션별 연산 컨텍스트 상세 (mechanism별)

토큰이 `session_id`별로 **load→process→save** 해야 하는 구체적 중간 상태.

### 6.1 AES-GCM (멀티파트 AEAD)
`EncryptInit → EncryptUpdate* → EncryptFinal` 동안 유지:
- 라운드키(키 스케줄) 또는 키 참조, IV로부터 유도한 **J0**와 현재 카운터,
- **GHASH 누적자**(인증 태그 계산용), 처리한 **AAD 총 길이**·**암/평문 총 길이**,
- 부분 블록 잔여(16B 미만), 방향(암/복호), 태그 길이.
- Final에서 태그 생성(암호화)/검증(복호). 복호는 태그 확인 전 평문 미확정.

### 6.2 AES-CTR (스트림)
- 키(스케줄), **현재 카운터 블록**, **스트림 내 바이트 오프셋**(부분 블록 잔여
  키스트림). Update마다 오프셋을 이어서 진행.

### 6.3 SHA-256 / SHA-512 / SHA3-224/256/384/512 (멀티파트 해시)
- 해시 **체이닝 상태**(SHA-2: 8×워드, SHA-3: 1600비트 스펀지 상태),
  **부분 블록 버퍼**와 채워진 바이트 수, **총 메시지 길이**.
- Update는 상태 load→흡수→save, Final은 패딩→출력. one-shot(`NCMP_CMD_DIGEST`)은
  컨텍스트 없이 처리, 멀티파트(`DIGEST_INIT/UPDATE/FINAL`)는 컨텍스트 id로 관리
  (→ 현재 mock은 `dev->digest_ctx[]`로 8개 동시 컨텍스트).

### 6.4 SHAKE-128/256 (XOF)
- 스펀지 상태 + **흡수 종료 여부** + **이미 스퀴즈한 출력 바이트 수**. 요청 길이만큼
  이어서 출력할 수 있어야 한다(우리 토큰에서는 key derivation 용도).

### 6.5 ML-DSA (전자서명/검증)
- 단일 파트 `CKM_ML_DSA`는 컨텍스트 최소(키 참조 + 입력 누적).
- hash-then-sign(`CKM_HASH_ML_DSA*`)은 **프리해시 컨텍스트**, 도메인/컨텍스트
  문자열, **hedge/deterministic 모드**를 유지. 키 재료는 NVM(N5)에서 load.

### 6.6 ML-KEM (키 캡슐화/공유비밀)
- encapsulate/decapsulate는 단발성. 컨텍스트는 입력 누적 정도만.
- **산출물인 공유비밀은 키 객체**로 생성되어 V4(세션) 또는 N5(토큰)에 귀속.

> 요약: **디지털 서명·해시·AEAD·스트림**은 세션 컨텍스트(V3)에 중간 상태를
> 반드시 유지해야 하고, **키 자체**는 NVM(N5)에서 로드한다.

## 7. 컨텍스트 생명주기와 스왑

- **할당**: `*Init` 명령 시 세션에 컨텍스트 생성(컨텍스트 id 부여).
- **유지**: SRAM 컨테이너는 4개뿐이고 세션은 최대 32개이므로, **컨텍스트는
  컨테이너와 독립적으로** 세션별 RAM 영역에 보관되어야 한다. 컨테이너는 "지금
  실행 중인 명령"의 작업 공간일 뿐, 세션 상태의 영구 거처가 아니다.
- **스왑(eviction/restore)**: 활성 컨텍스트가 많아 온칩 RAM이 부족하면, 비활성
  세션 컨텍스트를 **암호화하여** 보조 저장소로 스왑아웃하고 다음 명령 시
  스왑인할 수 있다(스왑 저장소가 NVM이라도 **평문 상태 금지**, 재부팅 후 복원
  불가 정책이면 세션 스코프 임시 영역 사용).
- **해제**: `*Final`, 오류, 세션 종료, 타임아웃 시 컨텍스트 zeroize 후 반환.
- **타임아웃/고아 컨텍스트**: 연결이 비정상 종료되면 남는 컨텍스트를 회수하는
  정책 필요(유휴 타이머 또는 연결 종료 통지 기반).

## 8. 동시성 · 일관성 · 복구

- **세션 격리**: 서로 다른 `session_id`의 명령이 인터리빙돼도 컨텍스트는 완전히
  분리. 한 세션의 Update 사이에 다른 세션이 실행되어도 안전해야 한다.
- **직렬화 지점**: 같은 세션의 명령들은 **논리적 순서**대로 처리되어야 한다(호스트
  `sequence_id` + 토큰 측 세션별 순서 보장). 동일 세션에 대한 동시 update는
  정의되지 않은 동작이므로 호스트/토큰이 순서를 강제.
- **NVM 원자성**: 키 생성/삭제·PIN 변경·플래그 갱신은 **원자적**이어야 한다(전원
  차단 중 부분 쓰기로 손상 금지). 저널링/더블버퍼/체크섬 권장.
- **재시도 카운터 순서**: "감소를 먼저 커밋 → 검증 → 성공 시 복구"로 리셋 우회 차단.
- **크래시/전원 복구**: 부팅 시 NVM 무결성 검사(N1~N8), 미완료 트랜잭션 롤백,
  휘발성 상태(V1~V8)는 전부 초기화. 진행 중이던 세션 연산은 **모두 폐기**된다.
- **소거(zeroize)**: 모든 민감 휘발성 데이터(V3·V5·V8, 복호 평문, 세션 키)는 해제
  즉시 0으로 덮어쓴다. 변조 감지 시 키 소거(선택적 자폭 정책).

## 10. 호스트 스택과의 대응 (참고)

| 토큰 측 개념 | 호스트 측 구현 | 파일 |
|--------------|----------------|------|
| session_id | STDLL 세션 → 프레임 헤더 | `ncmp_wire.h`, `new_host.c` |
| 세션 상한(슬롯8/전체32) | `cur_sessions` + `sess_lock` | `ncmp/stdll/ncmp_session.c`, `ncmp_limits.h` |
| 멀티파트 컨텍스트 id | `DIGEST_INIT/UPDATE/FINAL` | `ncmp/mock/mcu_scheduler.c` |
| 로그인/PIN | `ncmp_admin` 어댑터 | `ncmp/stdll/ncmp_admin.c` |
| 토큰 정체성(N1) | 부팅 스캔 → SHM 캐시 | `ncmp/daemon/main.c` |
| in-flight/스케줄(V7) | 슬롯 통계 3종 | `ncmp/daemon/comm_thread.c` |

> mock 토큰(`ncmp/mock/`)은 결정론적 스텁이라 컨텍스트를 단순화해 보관하지만,
> **실제 FX3 엔진은 위 V3를 세션별로 완전히 구현**하고, N1~N8을 NVM에 안전하게
> 저장해야 한다. 하드웨어 브링업 시 이 문서를 기준으로 저장소 레이아웃과 소거·
> 원자성 정책을 확정한다.
