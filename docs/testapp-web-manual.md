# Web Test App 사용자 매뉴얼 (상세)

Token NCMP **웹 Test App**의 화면·버튼·시험 절차를 처음 쓰는 사람도 따라 할 수
있도록 상세히 설명한다. 화면 캡션·색상은 **밝은(라이트) 테마** 기준이며, 우상단
버튼으로 어두운 테마로 바꿀 수 있다(§2). 설치·실행·시스템 설정은
[`testapp-web-deployment.md`](testapp-web-deployment.md), 내부 설계는
[`testapp-web-design.md`](testapp-web-design.md)를 참고한다.

상태·`FX3 · SuperSpeed` 배지를 보여준다.

## 1. 시작하기

1. 서버(`ncmp_web`)가 실행 중이어야 한다(설치·실행은 배포 문서 참고). 보통
   관리자가 `http://<서버IP>:8080/` 으로 띄워 둔다.
2. 브라우저에서 그 주소를 연다. PC·노트·태블릿 어디서든 접속할 수 있다.
3. 서버가 **접근 토큰**을 요구하도록 설정된 경우(배포 시 `token=` 지정), 헤더의
   **서버 토큰** 칸에 그 값을 입력해야 API가 동작한다(미입력 시 401 오류).
4. 화면이 뜨면 로그에 "웹 테스트 앱 준비 완료" 가 보인다.

## 3. 상단 툴바

토큰을 쓰기 전에 **데몬을 켜고 → 라이브러리를 로드하고 → 초기화**하는, 준비
단계 컨트롤이 모여 있다.

### 3.1 ncmpd 그룹 (물리 토큰과 통신하는 데몬)

- **transport(전송) 선택 ▼**
  - 기능: 데몬이 어떤 토큰과 통신할지 고른다.
  - 값: `real`(실제 FX3 USB 토큰, **기본값**), `mock`(소프트웨어 모의 토큰,
    하드웨어 없이 시험), `socket`(소켓 프레임 서버).
  - 설정: **기본이 real**이다. 하드웨어가 없으면 `mock`으로 바꾼다.
- **[데몬 시작]**
  - 기능: 선택한 transport로 `ncmpd` 데몬을 실행한다.
  - 목적: 토큰 명령을 중계할 데몬을 띄운다. 이게 떠 있어야 Initialize가 성공한다.
  - 참고: 실 FX3는 토큰 식별 조회에 수 초가 걸리므로, 버튼을 눌러도 **준비될
    때까지 기다렸다가** 상태 램프가 초록으로 바뀐다(“ncmpd 준비 대기 중…”).
- **[데몬 정지]**
  - 기능: 실행 중인 데몬을 종료한다.
  - 목적: 전송 방식을 바꾸거나 시험을 끝낼 때 사용.

> 데몬을 외부(관리자)가 이미 띄워 둔 경우, 버튼을 누르지 않아도 상태 램프가
> 초록으로 보이며 바로 로드/초기화할 수 있다.

### 3.2 facade 그룹 (PKCS#11 라이브러리)

- **모듈 경로 입력칸**
  - 기능: 불러올 PKCS#11 라이브러리(`libpkcs11_ncmp.so`) 경로.
  - 설정: 비워 두면 **서버 기본값**(안내 문구로 표시)을 사용한다. 보통 비워 둔다.
- **[로드]**
  - 기능: 위 경로의 라이브러리를 메모리에 올리고(dlopen) 모든 PKCS#11 함수를
    연결(dlsym)한다.
  - 목적: 토큰을 조작할 함수 진입점을 확보한다. Initialize 전에 먼저 수행.
- **[C_Initialize] / [C_Finalize]**: 로드와 슬롯 새로고침 사이의 툴바 버튼.
  C_Initialize로 라이브러리를 초기화(데몬 접속 + SHM 연결)하면 활성 슬롯이 채워진다.
  C_Finalize로 해제. (세션은 자동으로 열리지 않는다 — "세션 관리"에서 직접 연다.)
- **[슬롯 새로고침]**
  - 기능: 활성 슬롯 목록을 다시 조회한다(C_GetSlotList).
  - 목적: 토큰을 꽂았다 뺐거나 데몬을 바꾼 뒤 목록을 갱신.
- **[dlsym 점검]**
  - 기능: 라이브러리가 PKCS#11 함수 70개를 모두 export 하는지 확인한다.
  - 목적: 라이브러리가 온전한지 빠르게 진단. 결과(예 “70/70 함수 확인”)가
    로그에 표시된다.
- **라이브러리 정보 줄**: 초기화 후 Cryptoki 버전·제조사·설명·버전을 보여준다.

> **C_Initialize / C_Finalize는 툴바로(로드와 슬롯 새로고침 사이), 명령 기본값은
> "장치 현황 · SRAM" 페이지로.** 화면은 **좌측 그룹 네비 + 카드형 콘텐츠**로
> 구성된다(가로 탭 폐지).

## 4. 좌측: 활성 슬롯 + 그룹 네비게이션

좌측 사이드바 **맨 위에 "활성 슬롯" 패널이 상시 표시**된다(메뉴를 바꿔도 유지). 슬롯을
클릭하면 그 토큰이 선택되고 토큰 정보·세션·암호 명령이 그 슬롯을 대상으로 동작한다.
**슬롯마다 세션 ID가 다를 수 있으므로**, 작업 전에 대상 슬롯을 먼저 고른다(세션 표의
"세션 ID" 칸에도 각 세션의 slot이 함께 표시된다).

그 아래 그룹 메뉴를 고르면 오른쪽 **콘텐츠**가 카드 형태로 바뀐다. 현재 위치는
헤더의 **브레드크럼**(`그룹 › 메뉴`)에 표시된다. 그룹/메뉴:

- **장치 관리**: `장치 현황 · SRAM`(토큰 정보 + 명령 기본값; 활성 슬롯은 좌측 상단
  상시 패널) · `세션 관리`
- **암호 서비스**: `AES / SHA3`(해시) · `AES-GCM` · `ML-DSA / ML-KEM` · `난수 생성` ·
  `CI 명령 제어`
- **도구**: `파일 · 검증` · `PKCS#11 API 시험` · `시나리오`
- **모니터링**: `암복호화 속도 측정` · `활동 기록`(로그)

## 5. 콘텐츠 (선택한 슬롯에 대한 작업)

### 5.1 장치 관리 › 장치 현황 · SRAM

- **활성 슬롯**은 좌측 상단 상시 패널에 있다(§4). 여기서 선택한 슬롯이 조회 대상이다.
- **토큰 정보** `[조회]`: C_GetTokenInfo + C_GetMechanismList. 라벨·제조사·모델·
  시리얼·플래그·PIN 길이·최대 세션 수·HW/FW 버전 + **지원 메커니즘** 목록.
- **명령 기본값(접기)**: 로그인·세션 명령의 **기본값**(사용자·User/SO PIN·세션 ID·
  R/W). C_Initialize·`적용`·값 변경 시 각 페이지 입력칸으로 반영된다(👁로 PIN
  표시/숨김). (세션은 자동으로 열리지 않는다 — "세션 관리"에서 직접 연다.)

### 5.2 장치 관리 › 세션 관리 (Sessions + Authentication)

첨부 설계처럼 **좌우 2카드**로 구성된다.

**Sessions 카드** (최대 256개 휘발성 세션)
- **[새 세션]**: C_OpenSession으로 세션 핸들을 발급받는다. OPEN_SESSION을 구현/응답
  하지 않는 펌웨어(실 타겟 브링업 등)에서는 지연 후 실패할 수 있다 — 이때는 아래
  **ID로 추가**를 쓴다.
- **세션 ID(0~65535) + [ID로 추가]**: 토큰 OPEN_SESSION 없이 입력한 세션 ID를 와이어
  헤더 `session_id`로 쓰는 세션을 **즉시** 연다(adopt). **0도 유효한 시스템 세션**.
  여러 ID를 각각 열어 다중 세션을 둘 수 있다. (기본으로 자동 생성되는 세션은 없다 —
  세션 0을 쓰려면 "ID로 추가"에 0을 입력한다.)
- **[선택 세션 닫기] / 표의 [닫기]**: 세션을 닫고 목록에서 제거(adopt 세션은 토큰
  CLOSE 없이 닫힘). **[새로고침] / [토큰 상태 조회]**: 표 갱신 / 각 세션에
  C_GetSessionInfo 조회.
- **표**: `No · 세션 ID · 역할 · 관리`. 현재 세션은 강조(●)되고, 로그인하면 **역할**
  칸이 User/SO 등으로 표시된다. 세션이 없으면 "열린 세션이 없습니다" 안내.

**Authentication 카드** (선택 세션으로 실행; 로그인은 토큰 전체 세션에 적용)
- **Session ▼**: 활성 세션 선택기(현재 세션). 모든 per-세션 명령(난수·해시·GCM·파일
  검증 등)은 **이 세션**으로 전송된다. 각 암호 페이지에도 같은 선택기가 있다.
- **Role ▼**: `User` / `SO` / `ContextSpecific`.
- **PIN**: 로그인 PIN(👁 토글). mock 기본값 User `1234`, SO `12345678`.
- **[Login] / [Logout]**: 로그인/로그아웃(틀린 PIN은 `CKR_PIN_INCORRECT`가 정상 실패).
- **[Ping]**: 선택 세션에 C_GetSessionInfo를 보내 살아있는지 확인(슬롯·상태·플래그).

### 5.3 암호 서비스 (AES/SHA3 · AES-GCM · ML-DSA/ML-KEM · 난수 생성)

각 메뉴 상단에 **활성 세션 선택기**가 있으며, 세션이 열려 있어야 동작한다.

- **AES / SHA3** — 세 가지 카드:
  - **해시(단발)**: **해시 선택 ▼**(SHA‑256/512, SHA3‑224/256/384/512) + **입력 문자열**
    + **[C_Digest]**. 실 토큰은 SHA3만 지원(SHA‑2 미지원)하므로 SHA3 계열을 쓴다.
    내부적으로 C_DigestInit + Update + Final로 처리한다.
  - **AES-CTR(암·복호화)**: **동작 ▼** + **키 Hex**(16/24/32B) + **Counter Hex**(16B)
    + **입력 Hex** → **[실행]**. 사용자 키를 C_CreateObject로 올려 C_EncryptInit
    (CKM_AES_CTR) + C_Encrypt로 처리한다.
  - **멀티파트 digest(대용량)**: 64KB 이상 데이터를 여러 C_DigestUpdate로 처리.
    **데이터 크기** 입력 + **[Hex 시험파일 생성]**(64바이트/줄) 또는 **시험 파일 선택**,
    **update 청크(≤3968)** 지정 후 **[멀티파트 digest 실행]**. 결과에 digest·데이터
    크기·update 횟수 표시.
- **AES-GCM** — 두 가지 카드:
  - **단발 인증 암호화**: **동작 ▼**(암/복호) + **키·IV·AAD·태그 길이·데이터 Hex**
    (+복호화 시 태그) → **[GCM 실행]**. C_CreateObject + C_EncryptInit(CKM_AES_GCM)
    + C_Encrypt/C_Decrypt. 암호화 출력은 암호문·태그 분리 표시, 복호화는 평문.
    **[새 12B IV]**·**[지우기]**·**[자가검증(랜덤 키)]** 보조 버튼 제공.
  - **멀티파트 AES-GCM(대용량)**: 64KB 이상을 C_EncryptUpdate/Final(또는 Decrypt*)로
    스트리밍 처리. 키/IV/AAD/태그/청크 지정 + 입력 Hex 시험파일 생성·선택 →
    **[멀티파트 GCM 실행]**. 암호화 결과는 **암호문+태그 파일**, 복호화는 **평문 파일**
    로 저장되고(복호화 입력은 암호문+태그 파일), **[출력 파일 열기]** 로 확인.
- **ML-DSA / ML-KEM**: standalone facade(mode-2)에는 PQC 연산이 미구현(스텁)이라
  안내만 표시된다(전체 기능은 opencryptoki full 빌드 mode-1).
- **난수 생성**: **길이** 입력 + **[C_GenerateRandom]** 로 토큰 RNG 출력(16진수).

> 시험 데이터 파일은 **데이터 크기를 입력해 자동 생성**(Hex, 64바이트/줄)하거나
> **기존 파일을 선택**할 수 있고, 생성/암복호화 결과 파일은 `/files/<이름>` 으로 열람한다.
> 토큰 per-call 데이터 한도(3968B)보다 큰 청크는 서버/facade가 내부적으로 분할한다.

### 5.4 파일 / 검증 ★ (대용량 init/update/final + 실타겟 정확성 확인)

이 탭은 두 가지 목적을 가진다: ① **큰 데이터**(64KB 이상)로 multipart 해시
(init/update/final)를 시험하고, ② **실 타겟의 결과가 소프트웨어 계산과
일치하는지** 대조해 토큰이 정확히 동작하는지 검증한다.

- **테스트 파일 생성**
  - **크기** 입력 + 단위(바이트/KB/MB) + **이름**(비우면 자동) + **[파일 생성]**.
  - 목적: init/update/final 시험에는 데이터가 **64KB(65536바이트) 이상**이어야
    한다. 원하는 크기를 입력해 서버에 테스트 파일을 만든다(반복 가능한 패턴으로
    채움). 생성 시 참고용 SW SHA‑256도 표시한다.
  - 설정 팁: 처음엔 100000(약 100KB)이나 1MB로 생성해 본다.
- **파일 선택 ▼ / [목록 새로고침]**: 생성된 파일 중 시험 대상을 고른다.
- **해시 선택 ▼**: 비교에 쓸 해시 알고리즘.
- **[토큰 multipart 해시]**: 선택 파일을 토큰으로 **조각내어**(DigestInit →
  DigestUpdate 반복 → DigestFinal) 해시한다. 결과(16진수·처리 바이트 수)를 표시.
  - 목적: 한 프레임(64KB) 한계를 넘는 데이터를 init/update/final 경로로 처리하는
    것을 확인.
- **[▶ 실타겟 vs SW 비교]** (핵심)
  - 기능: 같은 파일을 **토큰 multipart 해시**와 **호스트 OpenSSL 계산**으로 각각
    구해 **일치(MATCH)/불일치(MISMATCH)** 를 판정한다.
  - 목적: 정상 동작하는 실 타겟이라면 두 값이 **일치**해야 한다 → 토큰이
    정확히 계산하는지 검증. **mock 토큰은 실제 해시가 아니므로 MISMATCH가
    정상**이며(안내 문구 표시), 펌웨어가 올라간 실 FX3에서 MATCH를 확인한다.
  - 설정: **세션이 열려 있어야** 한다. 파일·해시를 고른 뒤 누른다. 결과 상자에
    `token` / `SW` 해시와 `match` 가 나란히 표시된다.

### 5.5 PKCS#11 API 시험 (단위 API 1건 실행)

- **목적**: API 하나를 골라 파라미터를 채워 **한 번** 실행하고 요청/응답(JSON)을
  그대로 확인한다. 디버깅·학습·시나리오 스텝 설계에 쓴다.
- **API 항목 ▼**: 실행할 단위 기능(대부분 PKCS#11 함수) 선택.
- **파라미터 입력 영역**: 선택한 항목이 필요로 하는 값들(슬롯·세션·길이·PIN 등)이
  자동으로 나타난다. 슬롯/세션은 현재 선택/열린 값이 채워진다.
- **[실행]**: 호출하고 응답 JSON을 아래에 표시.
- **[▶ 시나리오에 스텝 추가]**: 지금 항목+파라미터를 **시나리오의 한 스텝**으로
  추가한다(시나리오 메뉴로 이동).

### 5.5-A CI 송수신 (원시 CI 프레임 직접 송수신)

- **목적**: PKCS#11 함수가 아니라 **CI(Command Interface) 단위**로 실 타겟에
  와이어 프레임을 직접 보내고 응답을 받아, **송신/수신 메시지를 raw(Hex)와
  parsed(해석) 형태로 동시에** 본다. 프로토콜·펌웨어 브링업 디버깅용.
- **슬롯**: 명령을 보낼 슬롯 번호(보통 0).
- **CI ▼**: 보낼 명령을 opcode+이름으로 선택(VD_PING, GET_TOKEN_PARAMS, RNG,
  OPEN_SESSION, LOGIN, DIGEST …). 선택 시 오른쪽에 파라미터 힌트 표시.
- **session_id**: 와이어 헤더에 실을 세션 id(기본 0). 세션 기반 CI는 보통
  OPEN_SESSION으로 받은 핸들을 넣는다.
- **CI별 입력 파라미터 p0~p7**: 각 파라미터를 **Hex**로 입력(공백 허용, 비우면
  생략). 예) RNG 길이 16 → p0 `10000000`(LE u32), LOGIN → p0 `01000000`(User)·
  p1 `00000000`·p2 `31323334`(PIN "1234").
- **[▶ 전송]**: 전송할 때마다 **디버깅 창**에 한 블록이 위로 쌓이며, 각 블록에
  **송신(TX)는 왼쪽·수신(RX)은 오른쪽(좌우 2열)** 으로 나란히, 각각 **raw(Hex,
  16바이트 정렬)** 와 **parsed**(frame_len·session_id·sequence_id·command_id(+CI
  이름)·ack(+CKR 이름)·payload_len·param[i])를 보여준다. 화면이 좁으면 자동으로
  위아래로 접힌다. **[디버깅 창 지우기]**로 비운다.
- 무응답 CI는 데몬의 USB 타임아웃(~5초) 뒤 "RX 없음 (timeout)"으로 표시된다.
- 이 탭은 facade(C_*)를 거치지 않고 서버의 **별도 ncmp_client**로 데몬에 직접
  보낸다(상태/슬롯 폴링을 막지 않도록 독립 락 사용).

### 5.6 시나리오 (단위 항목을 조합한 자동 시험)

여러 단위 작업을 **순서대로 묶어** 한 번에 실행하고, 스텝별 성공/실패를 본다.
회귀 시험·데모·반복 점검에 쓴다.

- **시나리오 선택 ▼**: `★`=내장 시나리오, `💾`=서버에 저장된 시나리오.
- **[불러오기]**: 선택한 시나리오를 편집 영역으로 가져온다.
- **[새로 만들기]**: 빈 시나리오로 시작.
- **[▶ 실행]**: 스텝을 위에서 아래로 실행하고, 아래 표에 스텝별 **PASS/FAIL**과
  상세(rc·반환값·match 등)를, 끝에 요약(“N PASS / M FAIL”)을 표시.
- **[저장]**: 현재 시나리오를 **이름**으로 서버에 영구 저장(브라우저를 바꿔도,
  캐시를 지워도 유지되고 다른 접속자도 공유).
- **[삭제]**: 선택한 서버 저장 시나리오 삭제(내장은 삭제 불가).
- **이름 입력칸**: 저장할 이름.
- **[내보내기(JSON)] / 가져오기(JSON)**: 시나리오를 파일로 주고받는다.

**단위 항목 팔레트(클릭해서 순서대로 추가)**
- 범주별(수명주기 / 슬롯·토큰 / 세션·로그인 / 암복호화·해시 / 파일·검증)로
  **단위 항목 버튼**이 나열된다. 대부분 PKCS#11 함수이며, PKCS#11에 없는 보조
  기능(데몬 제어·파일 생성·실타겟↔SW 비교)은 "도구"로 표기된다.
- 버튼을 **원하는 순서대로 클릭**하면 그 아래 **구성된 스텝**에 차례로 쌓인다.

**각 스텝 편집**
- **파라미터 입력**: 스텝마다 필요한 값을 그 자리에서 수정.
- **저장변수**: 그 스텝의 출력을 변수로 저장한다. 예: `openSession`은 기본으로
  핸들을 변수 `s`에 저장한다.
- **참조**: 이후 스텝의 파라미터에 `${s}` 처럼 쓰면 실행 시 그 변수 값으로
  치환된다. 그래서 `세션 열기(s 저장) → 로그인 ${s} → …` 가 클릭만으로 이어진다.
- **기대값 ▼**: 이 스텝이 `성공`/`실패`/`일치`/`불일치` 중 무엇을 기대하는지.
  (예: 잘못된 PIN 로그인 스텝은 `실패 기대`로 두면 실패해야 PASS. 실타겟↔SW
  비교 스텝은 `일치 기대`.)
- **↑ / ✕**: 스텝 순서 이동 / 삭제.

**내장 시나리오(예시)**: “Mock 전체 왕복”, “초기화 & 슬롯 조회”, “세션/로그인
수명주기”, “음성: 잘못된 PIN 로그인 실패”, “대용량 해시 검증(실타겟, ≥64KB)”.

## 7. 자주 쓰는 시험 절차 (요리책)

### 7.1 하드웨어 없이 기본 점검 (mock)
1. transport=`mock` → **데몬 시작**.
2. **로드** → **C_Initialize** (슬롯 목록이 채워짐).
3. 좌측 **장치 현황 · SRAM**에서 `Slot 0` 선택 → **토큰 정보 조회**.
4. **세션/로그인** 탭: **세션 열기** → PIN `1234`, User → **C_Login**.
5. **암복호화/해시** 탭: **C_GenerateRandom**, **C_Digest**, **AES‑GCM 자가검증**.

### 7.2 실 FX3로 점검
1. transport=`real` → **데몬 시작**(상태 램프가 초록이 될 때까지 몇 초 대기).
2. **로드** → **C_Initialize** → 슬롯 선택.
3. 이후 7.1과 동일. (펌웨어 미적재 보드는 토큰 정보가 비어 있을 수 있음)

### 7.3 대용량 해시 정확성 검증 (실타겟 vs SW)
1. 세션을 연다(§5.2).
2. **파일/검증** 탭: 크기 `131072`(128KB) → **파일 생성**.
3. 파일·해시(SHA‑256) 선택 → **▶ 실타겟 vs SW 비교**.
4. 실 타겟이면 **MATCH** 여야 정확. (mock은 MISMATCH가 정상)

### 7.4 로그인 음성 시험(잘못된 PIN)
1. 세션을 연다 → **세션/로그인**에서 PIN을 일부러 틀리게(예 `9999`) → **C_Login**.
2. 로그에 `CKR_PIN_INCORRECT` 가 뜨면 토큰이 올바르게 거부한 것.

### 7.5 시나리오로 자동화
1. **시나리오** 탭 → 팔레트에서 `데몬 시작 → 로드 → C_Initialize → 세션 열기 →
   C_Login → … → C_Finalize` 를 순서대로 클릭.
2. `세션 열기` 스텝의 저장변수를 `s`(기본)로 두고, 로그인·암복호 스텝의 session
   파라미터에 `${s}`.
3. 이름을 적고 **저장** → 다음에 **불러오기** → **▶ 실행**으로 반복 점검.

## 8. 문제 해결

| 증상 | 원인 / 해결 |
|------|-------------|
| 화면은 뜨는데 API가 **401** | 서버에 토큰 인증이 켜짐 → 헤더 **서버 토큰**에 올바른 값 입력. |
| **C_Initialize** 실패(예 0xE0) | 데몬 미기동/준비 전 → **데몬 시작** 후 상태 램프가 초록이 된 뒤 다시 시도. |
| 슬롯 목록이 비어 있음 | 데몬이 떠 있고 Initialize가 성공했는지 확인 → **슬롯 새로고침**. |
| 세션 작업이 "세션 없음" 안내 | **세션 관리**에서 먼저 **새 세션** 또는 **ID로 추가**. |
| 실타겟 비교가 **MISMATCH** | mock은 정상(가짜 해시). 실 FX3는 NCMP 펌웨어가 올라가 있어야 MATCH. |
| 로그인 `CKR_PIN_INCORRECT` | PIN 확인(mock User `1234`, SO `12345678`). |
| 저장한 시나리오가 안 보임 | 서버 저장 방식이므로 서버가 최신 버전인지 확인(관리자: 서비스 재시작). |

## 9. 용어

- **슬롯(Slot)**: 토큰이 꽂히는 논리 자리. 선택해서 해당 토큰을 조작.
- **세션(Session)**: 토큰과의 작업 단위. 열고(C_OpenSession) 닫는다(C_CloseSession).
- **로그인/SO/User**: PIN 기반 인증. SO=보안책임자, User=일반 사용자.
- **메커니즘(Mechanism)**: 알고리즘(예 CKM_SHA256, CKM_AES_GCM).
- **multipart(init/update/final)**: 큰 데이터를 조각내어 처리하는 방식.
- **transport**: 데몬이 토큰과 통신하는 경로(mock/real/socket).
- **facade**: 브라우저↔토큰을 잇는 PKCS#11 라이브러리.
